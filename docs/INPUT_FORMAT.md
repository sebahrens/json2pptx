# JSON Input Format — Tutorial

`json2pptx` accepts a JSON object describing a presentation and renders it into a `.pptx` file. This page documents the **raw compiled `PresentationInput` format** with worked examples; for the **canonical list of fields, types, enums, and required-vs-optional flags**, query the schema directly.

For new agent-authored decks, prefer the semantic deck spec instead of hand-authoring this raw format. The semantic compiler accepts compact YAML/JSON slide kinds such as `kpi_snapshot`, `chart_insight`, `comparison`, `roadmap`, `cycle`, and `decision`, then compiles them to the raw `PresentationInput` described here:

```bash
json2pptx semantic schema
json2pptx semantic validate --spec deck.yaml
json2pptx semantic compile --spec deck.yaml --output compiled.json
json2pptx semantic render --spec deck.yaml --output deck.pptx
```

Raw `PresentationInput` remains the power-user escape hatch, the compiler output format, and the contract for low-level MCP tools such as `validate_input`, `preview_presentation_plan`, `generate_presentation`, and `repair_slide`.

## Canonical schema (single source of truth)

- MCP: `get_input_schema` — returns the JSON Schema for `PresentationInput`, with `x-field-scope` (`deck` / `slide` / `content` / `shape` / `split`), inline `enum` arrays, and discriminator constraints. Digest-cacheable.
- CLI: `json2pptx input-schema` — same payload, printed to stdout.

Semantic specs have their own schema:

- MCP: `list_deck_archetypes`, `list_slide_kinds`, and `validate_deck_spec` expose the supported semantic contract.
- CLI: `json2pptx semantic schema` — prints the semantic JSON Schema.

The raw schema is generated from the Go input structs in `internal/deckinput` (aliased through `cmd/json2pptx/json_schema.go` for CLI compatibility). This tutorial only describes shapes and gives examples; the schema is authoritative on field names, types, and required-vs-optional.

## Minimum complete deck

```json
{
  "template": "warm-coral",
  "output_filename": "review.pptx",
  "slides": [
    {
      "layout_id": "title",
      "content": [
        {"placeholder_id": "title", "type": "text", "text_value": "Q1 Review"}
      ]
    }
  ]
}
```

A presentation is a top-level object with a `template` and a non-empty `slides` array. Each slide pins a layout via `layout_id` (canonical id, e.g. `title`, `content`, `two-column`, `section`, `blank`) or hints `slide_type` (`title`, `content`, `chart`, `section`, `two-column`, `diagram`, `image`, `comparison`, `blank`). At least one of the two must be set. `template` is a registered template NAME (a `.pptx` in the templates directory or the embedded set, without the extension) and never takes a path; `template_path` is the bring-your-own form — `{"template_path": "./client-brand.pptx", "slides": [...]}` — for a `.pptx` the engine has not registered. Set exactly one. On the CLI a relative `template_path` resolves against the deck JSON's own directory; over MCP against the call's `base_dir` (server CWD when omitted), and it must stay inside it after `~`/`$VAR` and symlink expansion — an escape is refused with `INVALID_PATH`. `examine_template`, `list_templates`, `validate_input`, `preview_presentation_plan`, `generate_presentation`, `score_deck` and `render_deck_spec` all accept it, and a `render_deck_spec` `deck_id` keeps the file and its `base_dir` for later deck_id-only calls; `get_started(task:"onboard-template")` walks the vetting sequence. Copying the file into the templates directory registers it live, no restart, as a normal `template`.
To preview the same input against another registered template without editing the deck, pass `json2pptx validate --template NAME --fit-report` (also works with `--json` / `--json-output`) or the top-level `template` argument to MCP `validate_input`. The override takes precedence over the presentation's `template` or `template_path` for that validation call only.

## A typical content slide

```json
{
  "layout_id": "content",
  "content": [
    {"placeholder_id": "title", "type": "text", "text_value": "Highlights"},
    {"placeholder_id": "body",  "type": "bullets", "bullets_value": ["Revenue +25%", "NPS at all-time high", "OpEx flat"]}
  ],
  "speaker_notes": "Hit the revenue point first."
}
```

A slide's `content` array is a list of typed items, each targeting a placeholder by its canonical id (`title`, `subtitle`, `body`, `body_2`, `body_3`, `image`, `image_2`). The schema enforces the `type` → typed-value pairing via an `if`/`then` discriminator chain:

- `type: "text"`             → requires `text_value` (string). A title or subtitle keeps the case of its number-unit tokens on templates that set titles in capitals (`modern-template`, `modern`, `abstract`, `blue-corporate`): `"Savings reach €2.2m in 6 mo"` renders `SAVINGS REACH €2.2m IN 6 mo`, not `€2.2M` / `6 MO`. A token is a number with one to four letters against it (`€2.2m`, `12bn`, `40k`, `3pp`, `10x`, `200ms`; not ordinals), or a number, a space and a unit abbreviation (`6 mo`, `2.5 pp`, `40 kWh`); a unit typed in capitals is left alone
- `type: "bullets"`          → requires `bullets_value` (string array); items typed `1. …`, `2. …`, `3. …` render as an auto-numbered list, and a list that counts up from a later number (`4. …`, `5. …`) keeps its typed numbers in place of the layout's glyph (see `NUMBERED_LIST_NOT_APPLIED` in [FIT_FINDINGS.md](FIT_FINDINGS.md)); leading spaces or tabs on an item nest it one level deeper. When the layout disables markers on its first body level (e.g. `abstract`), nested items are also unmarked and indented 18pt per level, so marker use stays consistent across levels
- `type: "body_and_bullets"` → requires `body_and_bullets_value`
- `type: "body_and_lead"`    → requires `body_and_lead_value` (`{"lead": "...", "bullets": [...]}`); the bullets are sized like plain bullets by the body density policy (18pt up to 6 paragraphs, 16pt from 7, 14pt from 10; an in-range template size is kept) and the bold, unbulleted lead one 2pt step above them (never under 16pt); autofit shrinks both together
- `type: "bullet_groups"`    → requires `bullet_groups_value`; groups are spaced by proximity (a header sits closer to its first bullet than bullets sit to each other, and the gap before the next header is at least 1.5× the bullet gap), and sub-bullets are indented at most 24pt from the header edge, whatever the template master declares
- `type: "table"`            → requires `table_value`
- `type: "chart"` / `"diagram"` → requires `chart_value` / `diagram_value`
- `type: "image"`            → requires `image_value`; with no `fit`, a picture placeholder cover-crops the image to its frame, while a body / content placeholder (every template without a picture layout) keeps the whole image, scaled to fit and anchored to the placeholder's top-left corner. `fit: "cover"` forces the crop (cover that discards more than 30% of an axis reports `IMAGE_HEAVY_CROP`); `fit: "contain"` keeps the whole picture centred. An image whose `placeholder_id` the layout lacks (`"image"` on a body-only layout, `"body"` on a picture-only one) is routed to the picture placeholder, else the largest free body, with an info `placeholder_remapped`. A picture that covers the footer band suppresses that slide's footer text / page number (`CHROME_OVER_IMAGE`). Legacy `value` image objects also accept `fit`. Check text/image contrast separately; see [native image guidance](../skills/template-deck/TEMPLATE_GUIDE.md#image).

A `table_value`'s `style.highlight_column` (1-based) fills that column's body cells with a 20% tint of the template's primary fill — the slot `list_templates` reports as `color_roles.primary_fill` (`accent1` on most templates, `accent2` on warm-coral, `accent3` on business-template, `dk2` on blue-corporate), in placeholder tables and `shape_grid` table cells alike. It used to be `accent3` on every template, which is an unrelated hue on most themes (blue on forest-green).

A `table_value`'s `headers` define its column count. Each row may use `col_span` / `row_span` on a cell (`{"content":"Total","col_span":2}`); a row that covers fewer columns than `headers` is padded with empty cells (a column still covered by a `row_span` from above keeps its merge), and a row that covers more columns is rejected by `validate` and `generate` alike (`INVALID_PARAMETER`, path `.../table_value.rows`). Other `*_value` fields are forbidden for the chosen type. The legacy raw `value` field is still accepted (unconstrained) for backward compatibility. `table_value`, `chart_value`, `diagram_value` and a `shape_grid` cell's `diagram` / `table` each take an optional `alt` — one sentence a screen reader announces, written into the shape's `cNvPr/@descr`; without it the engine derives one from the payload and reports `MISSING_ALT_TEXT` (advisory, see [FIT_FINDINGS.md](FIT_FINDINGS.md#missing_alt_text)).

Text content and source attribution can carry clickable links. Set `"link": {"url": "https://example.com"}` on a text or bullets content item to link its text runs (every bullet in a bullets item), or set `"source": "Annual report", "source_link": {"url": "https://example.com/report"}` on the slide. A slide `source` renders once in the source zone just above the footer (9pt italic, muted text colour, on the content's left edge); `chart-insights-split` / `stat-hero` `values.source` is lifted into it, and a data slide without any source draws `DATA_WITHOUT_SOURCE` (review weight). Top-level `source` is the deck-level default: every data slide (chart, table of figures, KPI / stat pattern) that has no source of its own — slide `source`, a lifted pattern source, or a `chart_value.footnote` — renders it, so a deck built from one data set states it once (DeckSpec: `meta.source`). URLs must be absolute HTTP/HTTPS URLs. A link object sets exactly one of `url` and `slide`.

## Section slides and the title-at-bottom convention

Section dividers (`layout_id: "section"` / `slide_type: "section"`) target a template's Section Divider layout. A slide counts as a section divider for auto-numbering when it declares `slide_type: "section"`, when its `layout_id` is `"section"`, or when the layout it names is the template's Section Divider (canonical type, or tagged `section-header`) — so a deck that reaches the divider through a template-specific layout ID still gets its sections numbered. In some templates the **visual order of the title and the decorative number is reversed** from a normal content slide: a large decorative "section number" frame sits at the top of the slide and the section *title* is placed in a smaller slot near the **bottom**. You still author it the same way — write the section title into the `title` placeholder — but the rendered title will appear lower on the slide than you might expect, and its capacity is small.

These layouts carry the `title-at-bottom` classification tag, and when the bottom title slot only fits a short single-line title they additionally carry `compact-title` (see the layout-tag tables in the template guide). When you see either tag, keep the section title to a short, single line (the reported per-layout `max_chars` on a title is the measured capacity of the box, which is not the same signal). Long, multi-line section titles overflow the slot. The decorative number is supplied by the template, not by your JSON.

**Unnumbered and relabelled dividers.** Back matter is not a chapter: a divider titled Appendix / Appendices / Backup / Annex / Q&A / Questions / Thank you gets no number and does not advance the count, so an Appendix after three chapters no longer renders as "04". A slide-level `section_number` overrides the automatic number on any divider: `false` suppresses it (and the divider is not counted), a short label of at most 4 characters (`"A"`, `"02"`, `"IV"`) renders verbatim, and a numeric label restarts the count from its value. In a `structure` block, `sections[].appendix: true` does the same for the whole section: an unnumbered divider, no entry in `auto_agenda`, and a running section of "Appendix: <title>" for `chrome.tracker` / `chrome.section_crumb`. Appendix slides — those after a divider titled Appendix / Appendices / Backup / Annex (up to the next ordinary divider), or in a `structure.sections[]` entry with `appendix: true` — are back matter for the rhythm checks too: they neither form nor extend a run for `DECK_MONOTONY`, `analyze_deck_rhythm` (`break_run`, `bullets_heavy`) or the DeckSpec `SEMANTIC_RHYTHM_MONOTONY` / `SEMANTIC_RHYTHM_DENSITY` warnings. A raw divider with only `section_number: false` does not open back matter; title it Appendix, set the slide-level `appendix: true` on the divider, give it a single-letter `section_number` such as `"A"` after numbered chapters (a deck that letters every chapter A, B, C is not an appendix), or use `sections[].appendix`.

**Continued exhibits.** An exhibit split across slides — a table too long for one — is one unit of the argument. Mark the parts in the title: a trailing `(1/2)` / `(2/2)`, `[2 of 3]`, `– 2/3`, or `(cont.)` / `(continued)` on the later parts, with the same title text before the marker. The parts then count once for every run check (`DECK_MONOTONY`, `analyze_deck_rhythm` `pattern_runs` / `motif_runs` / `break_run`, `score_deck`'s composition axis and the DeckSpec `SEMANTIC_RHYTHM_MONOTONY`), so following a "split the table" finding does not earn a monotony finding. Keep the parts adjacent: up to three slides sitting between two parts — typically a section divider inserted to break a run — are reported (`analyze_deck_rhythm` recommendation `continuation_interrupted`, `score_deck` composition diagnostic `continuation_interrupted` at 10 points, DeckSpec `SEMANTIC_RHYTHM_CONTINUATION_SPLIT`), because the divider's section then labels the second part.

**Appendix page numbers.** When the footer shows page numbers, back-matter slides read `A1`, `A2`, … in the slide-number position instead of continuing the main deck's count (go-slide-creator-khzni). The letter is the divider's single-letter `section_number`, the letter of an "Appendix B: …" title, or `A`; the count restarts per letter. The appendix divider itself shows no page number. Main-deck slides keep contiguous numbers — a slide after the back matter (a closing slide) continues the main count rather than its physical position — and a `{current} / {total}` format counts only the main deck (appendix slides show the bare label). Appendix labels are written as literal text, not PowerPoint's auto-updating slide-number field; a deck without back matter keeps the auto field on every slide. The DeckSpec `section` kind with `appendix: true` compiles to a raw divider with `appendix: true`.

## Inline formatting

Text and bullet strings accept five inline tags: `<b>`, `<i>`, `<u>`, `<sup>`, `<sub>` (the live list is `get_capabilities().features.supports_inline_markup`). They can be nested: `<b><i>bold italic</i></b>`. Plain dashes/arrows (`→`, `•`, en/em dashes) are allowed; **emoji codepoints are rejected anywhere** in deck JSON.

## A custom visual: `shape_grid`

For slides where placeholders aren't expressive enough, use `shape_grid` on a `blank` layout:

```json
{
  "layout_id": "blank",
  "content": [
    {"placeholder_id": "title", "type": "text", "text_value": "Strategic Pillars"}
  ],
  "shape_grid": {
    "columns": 3,
    "gap": 4,
    "rows": [
      {"cells": [
        {"shape": {"geometry": "roundRect", "fill": "accent1",
          "text": {"content": "Innovation\nR&D + emerging tech",
                   "size": 12, "color": "lt1", "vertical_align": "ctr"}}},
        {"shape": {"geometry": "roundRect", "fill": "accent2",
          "text": {"content": "Growth\nNew markets",
                   "size": 12, "color": "lt1", "vertical_align": "ctr"}}},
        {"shape": {"geometry": "roundRect", "fill": "accent3",
          "text": {"content": "Efficiency\nAutomation",
                   "size": 12, "color": "lt1", "vertical_align": "ctr"}}}
      ]}
    ]
  }
}
```

Shape text renders as written. Lines starting `- ` or `• ` are bullets, and two or more consecutive lines numbered `1. `, `2. `, `3. ` … are an auto-numbered list; any other line that opens with a number — a lone `"2. Enabler bar: funded first"`, a run that starts above 1 — keeps the number as typed.

Each cell holds exactly one of: `shape`, `table`, `icon`, `image`, `diagram`, or `composite` (plus, optionally, `layers` — below). A `diagram` cell renders through svggen as an embedded picture, except `swot` and `porters_five_forces`, which render as the same native OOXML shapes they draw in a body placeholder, sized to the cell; other native-only diagram types (`pestel`, `business_model_canvas`, `value_chain`, ...) still need a body placeholder. A raster `image` cell without an explicit `fit` fills its whole cell and is centre-cropped to it ("cover", via `a:srcRect`) — never stretched; with `fit` (`contain` / `fit-width` / `fit-height`) it keeps the square frame and is cover-cropped into it; SVG images keep the square frame. The image's own `fit` (`"cover"` default, or `"contain"`) sets how a raster picture sits in that frame: `"contain"` keeps the whole picture, scaled and centred (letterboxed), and never crops it — use it for screenshots whose edges carry evidence. An image cell's optional `geometry` (`"rect"` default, or `"ellipse"`) sets the picture frame's preset shape: `{"fit": "contain", "image": {"path": "jane.jpg", "geometry": "ellipse"}}` is a circular, cover-cropped headshot. Cells can span columns/rows via `col_span` / `row_span`; an empty spacer cell (`{}` or `{"col_span": 2}`) claims its span too. A numeric `columns` must be a whole number from 1 to 24, and a `columns` array may hold at most 24 widths (`INVALID_GRID` otherwise; the bound is `shapegrid.MaxColumns`). A `columns` array's widths and each row's `height` / `flex` / `min_height` / `max_height` must be finite and >= 0, and the widths must not all be 0; `validate` rejects anything else. A cell's `max_height` (points) caps its rendered height and centers it in its row. A cell's `bleed_left` (points, `>= 0`) extends its shape that far past the cell's left edge, over the column gap and into the previous cell's rectangle, without moving any cell — it is how a chevron's tail tucks under the point before it (`value-chain`). `bleed_top` does the same upward into the row above, and `inset_top` / `inset_bottom` pull the shape's top / bottom edge in from the cell's (all points, `>= 0`); together they step a row of cells up a staircase while the grid keeps one row per kind of cell (`journey-maturity-model`). A row's `rule` (`"above"`, `"below"` or `"both"`) draws a full-width 0.75pt hairline (`dk1` at 30%) in the middle of the gap above / below the row; it takes no height and no row index, so `links` and overlay `anchor_cell` rows are unaffected (`swimlane` `tiles` lanes). A row's `band` is a fill (a scheme colour string or a `{color, alpha, lumMod, lumOff}` object, as on a shape): one unlined rectangle as wide as the grid and as tall as the row, drawn behind the row's cells and behind every connector; it takes no height and no cell, so row and cell addresses are unchanged. A band is a backdrop: it is not counted as content by `SLIDE_UNDERUSED` (`swimlane` lanes). A row's `connector` and a `links[]` entry's `connector` take `style` (`"arrow"` / `"line"`), `color`, `width` (points), `dash` and `head` — the arrowhead size of an `"arrow"`: `"sm"`, `"med"` (default) or `"lg"`, drawn about 2× / 3× / 5× the line width. Compose (horizontal and vertical) places each segment in a nested grid so it keeps its own column widths, gaps, row heights (including `min_height` / `max_height`) and alignment; a vertical segment gets a full-width row sized by its `size_pct`. Slide-level `overlays` can float arrows, lines, badges and callouts over the grid; anchor them to cells by `(row, col, at)`, to a point on an image cell's picture (`anchor_image`, below) or by percent-of-slide coordinates. Grid-level `vertical_align` (`"stretch"` default, `"top"`, `"center"`, `"bottom"`, `"auto"`) places a block of `max_height`-capped rows inside the bounds instead of stretching it; `"auto"` hangs the block from the template's body line (the body placeholder top) whenever the template has one, and otherwise top-anchors a block filling at most 60% of the bounds and centres a fuller one — except on a slide's own grid without `bounds`, where a block that needs under 75% of the content area is composed: its text takes one step up the type scale (12→14pt, 14→18pt, display figures ×1.2 up to 48pt) with rows and row gap grown 1.15–1.35× when that still fits, and the block sits at the optical centre (45% of the spare height above it, never above the body line). `"top"` keeps such a block on the body line at its authored sizes, and `type_scale: "compact"` keeps the sizes. Default (full-area) grid bounds start at the body line too, but never lower than 9pt under the title box: where a template's body placeholder sits further below its title box (p-style ~11pt, modern-yellow ~19pt, business-template ~28pt) a full-height grid starts at the title-box line so dense patterns keep the height their schema maxima are sized for. Named patterns expand with `"auto"`; a slide `pattern.vertical_align` overrides it. When rows over-commit the grid, a row held at its `min_height` keeps it and the other rows give way. **Text margin:** every shape's text sits 0.5 cm (~14.17pt) from the shape edge on all four sides, on every template — it is the engine default and needs no field. A shape's `text` object may override a side with `inset_left` / `inset_right` / `inset_top` / `inset_bottom` (points, `>= 0`); each authored side replaces only that side, the others keep 0.5 cm. Named patterns never override it. One exception keeps title, body and exhibit text on one left line: an unfilled, unoutlined, left-aligned text shape in a grid's first column (no explicit `inset_left`, no icon) has its left margin reduced so its text starts at the slide title's text edge (title X + its `lIns`). A shape too small for one line of its text plus the margin on an axis (a pill, a badge, a thin band) has that axis's margin shrunk to what still leaves one line, never below zero, rather than shrinking the text. Budget rows for the margin: a one-line 12pt row needs about 43pt, two lines about 57pt. **Co-located shapes: cell `layers`.** A cell may stack further native shapes inside its own rectangle — the segments of a ring, a numbered badge on one, a centre label: `{"fit": "contain", "layers": [{"name": "segment-1", "frame": {"x": 0, "y": 0, "w": 1, "h": 1}, "shape": {"geometry": "blockArc", "fill": "accent1", "line": "none", "adjustments": {"adj1": 16200000, "adj2": 0, "adj3": 20000}}}, {"name": "badge-1", "frame": {"x": 0.72, "y": 0.06, "w": 0.2, "h": 0.2}, "shape": {"geometry": "ellipse", "fill": "dk2", "line": "none", "text": {"content": "1", "size": 12, "color": "lt1", "align": "ctr", "vertical_align": "ctr"}}}]}`. `frame` places the layer: `x`, `y` (top-left corner) and `w`, `h` (size) are fractions (0–1) of the cell's **fitted bounds** — the rectangle the cell's own shape gets. With `fit: "contain"` that is the centred square, so `{"x": 0, "y": 0, "w": 1, "h": 1}` is the square a circle is drawn in, not the wide cell around it; `bleed_*`, `inset_*` and `max_height` move the frame with the shape. `w` and `h` must be greater than 0 and the frame must stay inside the cell (`x + w <= 1`, `y + h <= 1`, with 0.0001 of slack for computed values); one that does not is refused (`INVALID_SLIDE`, message `… layers[1] ("badge-1"): LAYER_FRAME_OUT_OF_CELL: …`), naming the layer by index and by its optional `name`. `shape` is a shape exactly as in a cell — `geometry`, `fill`, `line`, `text`, `rotation`, `flip_h`, `adjustments`, `type_scale`, `link` — written, measured and checked by the same code — including `shape.icon`, an icon overlay laid out inside the layer's frame (centred on a textless shape, 60% of its shorter side unless `scale` says otherwise; its source, `fill` and alt text are checked at `…/layers/<index>/shape/icon`). Z-order: the cell's own content first, then its layers in array order, so a later layer sits on top; row connectors and `links` stay behind every cell, accent bars and slide `overlays` on top, and icons — pictures — above every shape of the grid, so never cover a layer's icon with a later layer. A cell may hold only layers (a transparent canvas); layers combine with `shape`, `icon` or `image` and are refused beside `table`, `diagram`, `composite`, `pattern` and `grid`; with `group: true` the cell's shape and its layers are written into one group. Layer text counts like cell text — capacity budgets, autofit, `TEXT_BELOW_READABLE_MIN`, `fit_overflow`, geometry and contrast findings — and is reported at `<cell path>/layers/<index>` (text at `…/layers/<index>/shape/text`; `reduce_cell_text` takes that path as `cell_path`). A layer does not size its row (`auto_height` reads the cell's own text), is not a connector or `links` endpoint, does not share its row's autofit, and does not receive `defaults.cell_style` or `named_style`.

**Exhibit callouts on a screenshot or photo.** An overlay endpoint can target a point on a `shape_grid` image cell's source picture: `{"anchor_image": {"row": 0, "col": 0, "x": 0.35, "y": 0.54}}` in fractions of the image (0–1 from its top-left corner), or `{"anchor_image": {"row": 0, "col": 0, "x": 560, "y": 484, "units": "px"}}` in the file's intrinsic pixels. The point resolves through the same cover / contain transform that places the picture, so it stays on its pixel when the frame aspect, the image `fit` or the template changes; setting both `anchor_cell` and `anchor_image` is an error, as are coordinates outside the image. `kind: "callout"` draws a native 12pt bold label (`text`, required) whose top-left is `from` — sized to its text unless `width` / `height` (slide percent) are given, filled with `color` (default `accent1`) and inked white or near-black, whichever contrasts more — plus a leader from the label's edge facing the target to `to`, ending in a dot; the leader never crosses its own label. A callout whose `to` is an `anchor_image` point may omit `from`: the label is then placed beside its target, inside the picture's frame and clear of the other callouts' targets and labels (`{"kind": "callout", "text": "1  Delayed queue", "to": {"anchor_image": {"row": 0, "col": 0, "x": 0.35, "y": 0.54}}}`). When the addressed cell hosts a nested grid (a pattern that stacks a caption under its picture), `anchor_image` resolves to the one picture inside it. DeckSpec authors write these as `image_case.callouts`. A target the picture's cover crop trims away is reported as `OVERLAY_TARGET_CROPPED` (review) instead of being pointed elsewhere: an arrow or line is omitted, a callout keeps its label and wording without a leader, and a badge sits at the nearest visible picture edge. See `examples/exhibit-callouts.json` (wide, square and contain frames).

```json
"overlays": [
  {"kind": "callout", "text": "1  Delayed queue", "from": {"x": 68, "y": 24}, "to": {"anchor_image": {"row": 0, "col": 0, "x": 560, "y": 484, "units": "px"}}}
]
```

To make a grid shape or a free-floating badge navigate within the deck, set `"link": {"slide": 12}` on its `shape` or `overlays[]` badge object. Slide numbers refer to the final deck, starting at 1. Out-of-range slide targets are rejected. The generated shape is clickable across its full area.

## Named patterns (prefer over hand-built grids)

For common business slide shapes — KPI cards, process flows, BMC canvas, matrix-2x2, roadmap, strategy house, SCQA summary, agenda, comparison, pull-quote — use a named pattern instead of hand-authoring a `shape_grid`. Patterns are registered in `internal/patterns/` and discoverable via:

- MCP: `list_patterns`, `show_pattern`, `expand_pattern`, `recommend_visual`
- CLI: `json2pptx patterns list`

Pattern field shapes and overrides are documented in `docs/PATTERNS.md`. An expansion can be edited and resubmitted as a `shape_grid`: it carries `source: "pattern:<name>"`, which exempts the engine's own font sizes from constrained mode's absolute-size rule — keep the stamp, or those sizes are refused as if you had written them (raw hex is refused either way).

## Charts and diagrams

```json
{
  "placeholder_id": "body",
  "type": "chart",
  "chart_value": {
    "type": "bar",
    "title": "Revenue by Quarter ($M)",
    "data": [
      {"label": "Q1", "value": 12},
      {"label": "Q2", "value": 18}
    ],
    "subtitle": "FY2026, by quarter",
    "footnote": "Source: Internal finance data, FY26 close"
  }
}
```

`chart_value.subtitle` renders under the chart title and `chart_value.footnote` at the chart's bottom edge (bar, line, area, stacked, scatter, pie and donut charts); both are optional. A chart with a `footnote` counts as sourced for `DATA_WITHOUT_SOURCE`. A chart in a slide placeholder does not print its `title` when the slide's own title already carries it — the two are equal, or the slide title contains the chart title word for word ("Revenue by region" under "Revenue by region: EMEA leads"; case and punctuation ignored). The plot takes the freed height, and the title still feeds the alt text. A chart title that adds a unit or a period the slide title lacks ("Revenue by region ($M)") is kept; `subtitle` and `footnote` are always drawn. With `viewing_mode: "present"` (the default) every chart label — ticks, data labels, legend, axis titles, captions — is at least 12pt on the slide; `"read"` keeps the 10–11pt label floors (chart label floors are the one place the viewing mode changes what is drawn). Several filled areas in one area chart are opaque and painted tallest first, so they do not mix where they overlap.

Supported chart types (canonical names, as `get_chart_capabilities` and `recommend_visual` emit them): `bar`, `line`, `pie`, `donut`, `area`, `radar`, `scatter`, `bubble`, `stacked_bar`, `stacked_area`, `grouped_bar`, `small_multiples`, `waterfall`, `funnel`, `gauge`, `treemap`. Every type is also accepted with a `_chart` suffix (`bar_chart`, `line_chart`, …, `waterfall_chart`) wherever a chart type is read — `chart_value.type`, a compose `diagram.type`, a DeckSpec `chart.type`, a `secondary.type` and `recommend_visual` `candidates`; responses write the canonical short name. **Small multiples** take `{"categories": [...], "series": [{"name": "North", "values": [...]}, ...]}` with 2–6 panels, one per named series (the name is the panel title); every panel shares the categories and, by default, one y domain computed from all panels so magnitudes compare (`data.y_scale: "shared"`); `data.y_scale: "independent"` gives each panel its own axis and prints "Independent y-axes: … compare shapes, not levels" under the title. Plots are equal-sized and aligned with one tick precision; y tick labels sit on the left column (every panel when independent). `data.highlight` (panel names / indices) keeps those panels in the accent and greys the rest; `data.colors` overrides per panel. Fewer than 2 or more than 6 panels, an unnamed panel, `time_strings` / `time_values`, or an unknown `y_scale` fail validation; a placeholder too small for any panel grid to meet the readability floors (a 3-tick plot height, category labels that fit, panel titles that fit) reports `chart.plot_area_collapsed` with action `shrink_or_split` and `fix.params.max_panels_per_slide`. Waterfall charts require `data.points` with an explicit `type` on every point (`increase`, `decrease`, `subtotal`, or `total`). A flat label-to-value map is rejected: its numbers do not say whether a bar changes the running balance or shows an absolute balance. For a profit bridge, use `{"points":[{"label":"Revenue","value":21.3,"type":"total"},{"label":"COGS","value":-6.7,"type":"decrease"},{"label":"Gross Profit","value":14.6,"type":"subtotal"}]}`. Pie and donut slice labels show calculated share percentages by default. Explicit `style.value_format.style: percent` formats those shares (40 and 60 become 40% and 60%, without a scale warning); explicit `plain`, `compact`, or `currency` formats raw slice values. `decimals`, `prefix`, and `suffix` apply in either mode. **Percent units.** `style.value_format.input_scale` declares what percent data means: `fraction` (0.25 → 25%, 1.2 → 120%) or `percentage_points` (0.25 → 0.25%, 25 → 25%); ticks and labels share it, and it is rejected with any style other than `percent`. Omitted (or `auto`), values all within [-1, 1] are read as fractions (info `chart.percent_scale_ambiguous`) and larger values as percentage points (warning `chart.percent_scale_ambiguous`). Chart data rules enforced by the renderer: **Waterfall direction and totals.** `type` sets the direction: a `decrease` always lowers the running total and an `increase` raises it, whatever sign `value` is written with (`{"type":"decrease","value":5}` is a −5 step). A `total` / `subtotal` that differs from the running sum of the preceding bars by more than 0.5% is still drawn at its authored value and raises `chart.waterfall_total_mismatch` (review, fix `replace_value`). Label and tick precision is chosen to keep values distinct; a tiny delta never prints as `-0.0`. **Non-negative charts.** `stacked_area_chart`, `funnel_chart` and `radar_chart` reject negative values at validation (use `stacked_bar_chart` for signed stacks, a waterfall for losses, a bar chart for signed scores). `bubble_chart` rejects negative sizes. **Bubble size.** Bubble area is proportional to size on one scale shared by every series: the largest size in the chart draws the largest bubble, equal sizes draw equal bubbles in any series, and a zero size draws a minimum 3pt dot. **Stacked-area labels.** `show_values` labels each band with its own authored value, not the running total the band's edge sits at; series keep the same palette colours as the other Cartesian chart types. **Gantt / timeline dates.** A present but unparseable `start`/`start_date`/`end`/`end_date`, an end before its start, and (gantt) a task with neither `start_date` nor `date` are rejected, naming the field. A `time_unit` that would draw more than 200 axis ticks over the date range is coarsened (day → week → month → quarter → year) and reported as `chart.tick_thinned`. **`data.data_labels`** accepts an object (`format`, `show_on`) or a bool: `true` is shorthand for `{}` (labels on with defaults), `false` leaves them off. **`matrix_2x2`** accepts a reversed axis (`x_min > x_max`, as the BCG preset uses); points are clamped to the axis span, not pinned to one edge. **Bar highlight and labelled charts.** A single-series bar chart paints its bars neutral (dk1 at 38%) and only the highlighted ones in accent1: `chart_value.highlight` (or `data.highlight`) lists 0-based category indices and/or category names; omitted, a time series (years, quarters, months) accents its last bar and any other chart its largest; `[]` accents none; an entry that names no category fails validation. On a multi-series line, area or grouped / multi-series bar chart `data.highlight` names SERIES (0-based indices or series names): those keep the palette (accent1 first) and every other series turns dk1 at 38% (thin lines without markers or values on a line chart, labelled in grey at the line end); line-end series labels use the series colour, shaded to 4.5:1 against the background when it is too light for text; omitted, the one series named by the slide title or takeaway is highlighted, otherwise every series keeps the palette. **Labelled by default.** Omitting `style.show_values` labels bar-family charts with at most 16 bars (categories × series) and single-series line / area charts with at most 12 points, on the raw chart path and inside patterns alike; `style.show_values: false` or `data.data_labels: false` opts out. When every bar is labelled, bar and waterfall charts drop the value axis and gridlines for a 0.75pt dk1 baseline (an authored y-axis title is kept), bars take 60% of their slot and labels are 10pt (bold on highlighted bars) with a true minus sign (U+2212). A labelled single-series line / area chart likewise drops its gridlines and value-axis ticks (keeping an authored y-axis title). Line charts draw point markers only up to 12 points. Stacked bars label each segment in the chart's one value format at 10pt or more (a segment too small for its label goes unlabelled) and print a bold total above each stack. **Sort and orientation.** `data.sort` (`desc` | `asc` | `none`) orders bar-family charts by value (multi-series by category total); a single-series `bar_chart` whose categories are neither periods nor an ordinal scale (ranges, stages, low/medium/high) sorts `desc` by default. `data.orientation: "horizontal"` on `bar_chart` / `grouped_bar_chart` / `stacked_bar_chart` draws the category names right-aligned in a left column and the values past the bar ends; negative values get their own label column between the names and the bars. In a flat `{label: value}` map, string-valued `sort` / `orientation`, array `highlight`, bool / object `data_labels` and `group_small_below_pct` are directives, not categories. **Pies and donuts** sort largest-first clockwise from 12 o'clock (`data.sort: "none"` keeps the authored order), label up to 6 slices "Name  NN%" with no legend (`style.show_legend` forces one), fold slices under 3% into a trailing "Other" when two or more qualify (`data.group_small_below_pct`, 0 never folds; a highlighted slice is never folded), spread neighbouring outside labels apart with leader lines, and paint `data.highlight` slices accent1 with the rest in neutral greys. **Treemaps** print each cell's name and value (plus its share of the whole unless the values already sum to 100) by default; `style.show_values: false` shows names only. **Series colours** follow the template data palette, but a template's semantic positive / negative accent and any near-black accent go behind every other usable colour, and text inks (dk1 / dk2) are never a series colour; a pale accent is darkened to 2:1 rather than replaced. Waterfalls paint decreases accent1, increases a 55% accent1 tint (or a shade of accent1 when the tint falls under 3:1) and totals / subtotals dk1 at 60%. **Zero baseline and `y_min` / `y_max`.** Bar-family, line, area and waterfall charts start their value axis at zero whenever no plotted value (for a waterfall, no running total) is negative: a bar's length and a band's height are read from the baseline, and a count or revenue line zoomed onto its own range overstates the trend (an EBITDA bridge 24 → 31 on an axis starting at 22 showed the opening total as a stub). `data.y_min` and `data.y_max` (numbers) zoom the axis on purpose — an index around 100, a bridge whose steps are small against its totals; a chart whose `y_min` is above zero keeps its value axis so the truncation is visible, even when every bar is labelled. `y_min` must be below `y_max`; a `y_min` above the lowest plotted value or running total, or a `y_max` below the highest, is rejected at validation naming the field (the bar would be cut). The bounds are rounded outward to the nearest tick (`y_min: 1` on a 2-step axis draws 0). A `y_min` that hides more than half of the smallest bar drawn from the baseline (a bar, a stack, a filled band or a waterfall total) reports `chart.axis_not_zero` (action `info`). In a flat `{label: value}` map a numeric `y_min` / `y_max` is a directive, not a category.

### Legend defaults: direct labels for 2–4 series

Bar / line / grouped-bar / area charts with 2–4 series default to **inline series labels** (at the line endpoint, or above the last bar of each series) in place of a legend — per `tokens.ChartDirectLabelMaxSeries`. Above 4 series the legend reappears because in-plot labels collide. Force the legend back on with `chart_value.style.show_legend: true`. Line labels whose series end close together are stacked apart with a leader back to each line; when even stacked they will not fit, the chart draws a legend and reports `chart.overflow_suppressed`. Stacked variants and non-Cartesian chart types (pie, donut, scatter, radar, waterfall, funnel, gauge, treemap) are unaffected.

### Per-slide chart-style overrides

Add an optional `chart_style` block on a `chart_value` (or `diagram_value`) to flip an executive-default token for one chart; omit it to keep the deck-wide defaults. `show_vertical_gridlines` (default `false`) draws vertical gridlines on bar/line/area charts in addition to the horizontal ones, and `show_single_series_legend` (default `false`) renders the legend even for a single-series chart (normally suppressed because the title carries the label). See the schema for the authoritative field set.

```json
{
  "placeholder_id": "body",
  "type": "diagram",
  "diagram_value": {
    "type": "swot",
    "data": {
      "strengths":     ["Strong brand", "Loyal customers"],
      "weaknesses":    ["High costs"],
      "opportunities": ["Emerging markets"],
      "threats":       ["Competition"]
    }
  }
}
```

Supported diagram types: `timeline`, `process_flow`, `pyramid`, `venn`, `swot`, `org_chart`, `gantt`, `matrix_2x2`, `porters_five_forces`, `house_diagram`, `business_model_canvas`, `value_chain`, `nine_box_talent`, `kpi_dashboard`, `heatmap`, `fishbone`, `pestel`, `panel_layout` (aliases `icon_columns`, `icon_rows`, `stat_cards` expand to `panel_layout` with the matching `layout`, given inside `data`; each `panels[]` entry accepts a native-SVG `icon`). In `layout: "stat_cards"` the NUMBER is the hero: an explicit `value` wins, otherwise a short `body` carrying a digit (`"EUR 184m"`) is drawn at 32pt with `title` as its caption, so `{title, body}` and `{title, value}` render the same card; a prose `body` stays small under the title. A `heatmap`'s `values` rows must all have the same length, and `row_labels` / `col_labels`, when given, must match the row / column counts — `validate` rejects ragged grids and label-count mismatches; a `diverging` `color_scale` whose range spans zero is centred on 0. See `ChartSpec.type` and `DiagramSpec.type` in the schema for the authoritative list.

`house_diagram` data is `roof`, `sections` (the pillar row), `floors` (further levels: a string or `{label, items?}` band, or a `{sections: [...]}` row of cells) and `foundation`; any other `floors` shape is refused at its field rather than dropped — see `docs/diagrams/house.md`.

**Native framework surfaces.** The native framework diagrams — `swot`, `business_model_canvas`, `pestel`, `nine_box_talent`, `porters_five_forces`, `value_chain`, `kpi_dashboard` and the panel family (`panel_layout`, `icon_columns`, `icon_rows`, `stat_cards`) — draw the same surface as the named patterns: square-cornered cards on the template's neutral tints (`dk1` at 4%, 8% for a panel header band or the value-chain margin, 16% for value-chain primary activities), no outline, and a bold left-aligned title in the template's primary accent (or the first theme ink that reads where the accent does not). One accent, plus neutrals; `business_model_canvas` matches the `bmc-canvas` pattern cell for cell. Colour beyond that is kept only where it is data: `nine_box_talent` score bands (`semantic_accents` positive / neutral / negative), `porters_five_forces` intensity steps (three tints of `accent1`; an unscored force sits on the neutral card), `heatmap` scales, and the up / down trend ink of `kpi_dashboard` and `stat_cards` deltas. `swot` no longer tints its negative half in a second accent: the polarity is in the four labels and the fixed grid. Set `style.colors` to get accent-tinted cards back — entries apply in cell order and a short list repeats, so `["accent1","accent2"]` restores the two-tone SWOT, `["accent1","accent2","accent3","accent4","accent5","accent6"]` a per-cell rotation, and `["accent4"]` recolours the whole framework. `style.colors` applies to `swot`, `pestel`, `business_model_canvas`, the panel family (header bands; stat cards), `kpi_dashboard` (cards) and `value_chain` (support bars and primary activities, each counted from the first entry); authored colours keep the square corners and left-aligned titles, with titles in the text ink.

**Timeline event labels.** The `timeline` diagram draws every event label whole: on one line above its marker, staggered above / below when neighbours are close, wrapped onto two lines, and at a smaller shared size, in that order. A label that still cannot be shown is cut with an ellipsis and reported as `diagram.label_truncated` with action `shrink_or_split` — shorten it, use fewer events or spread their dates. Descriptions wrap in the slot between the neighbouring described events.

Charts and diagrams render to SVG and embed into the slide.

## Theme override

The deck's visual identity comes from the chosen `template`. Override deck-wide colors or fonts with `theme_override`:

```json
{
  "theme_override": {
    "colors": {"accent1": "#E31837"},
    "title_font": "Georgia",
    "body_font": "Arial"
  }
}
```

Each `colors` value must be six hex digits with an optional leading `#` (`#E31837` or `E31837`). Three-digit shorthand (`#abc`), color names (`navy`) and anything else are rejected by `validate` / `generate` with code `invalid_color` at path `/theme_override/colors/<slot>`, because the value is written verbatim into the theme part. Font names are inserted literally (XML-escaped; `$` has no special meaning); a font name containing control characters is rejected with code `INVALID_PARAMETER` at `/theme_override/title_font` or `/theme_override/body_font`. In `design_mode: "constrained"` (the default), raw hex colors are restricted; switch to `design_mode: "free"` for exploratory/artistic decks.

## Viewing mode and readability

Top-level `viewing_mode`: `"present"` (default, projected: 12pt body, 10pt captions, 20pt titles) or `"read"` (on-screen/print, lower floors). It never changes rendering; text shrunk below its role's floor is reported as `TEXT_BELOW_READABLE_MIN` (see `docs/FIT_FINDINGS.md`). Top-level `type_scale` controls measured growth of sparse `shape_grid` text: `"compact"` (raw default; no growth), `"comfortable"` (up to 70% of usable height, body/caption/KPI caps 14/12/40pt), or `"presentation"` (up to 80%, caps 18/14/48pt). A semantic DeckSpec defaults to `meta.type_scale: "comfortable"`. Pattern-level `overrides.type_scale` wins over the deck policy; a raw `shape_grid.type_scale` or `shape.type_scale` can override it for a grid or cell. Dense text is not enlarged, and authored font sizes are never reduced by this setting. Independently of `type_scale`, sized `shape_grid` text settles onto the type scale 28 / 18 / 14 / 12 / 10pt (11pt is the dense-body step): an off-scale size such as 13, 16 or 20pt renders at the step at or below it (12, 14, 18pt). Display figures (a short run containing a digit at 18pt or more — KPI values, step numerals), text of 28pt and above, and a `design_mode: "free"` deck's own grids keep their sizes; pattern expansions always snap. A two-column slide whose `body` and `body_2` bullet lists both open with a short label line (e.g. "Open-weight models" over longer points) renders that line as a bold column header without a bullet. Each grid paragraph keeps its source role (a display-size figure is a KPI value; display words are not, and a lone index marker such as an axis "1" is a caption) through to its written runs: a written size below that role's floor, or a populated frame with no usable area after insets, refuses publication even with `strict_fit: "off"`, without deleting source text or overwriting an existing destination. Preflight predictions stay advisory. Enlarge the frame or redesign the layout, keeping every required item; character budgets are sizing hints, so validate and inspect the rendered slides.

## Footer, page numbers, and structure

`footer`, `chrome.page_numbers`, and `structure.sections` configure deck chrome and section grouping. See the schema for the full set; agents typically only set `footer.enabled` and `footer.left_text`. When both `footer` and `chrome` are set, enabled `footer.left_text` is retained after any distinct text composed from `chrome`; a page-number-only `chrome` block leaves the legacy line intact; `chrome.page_numbers.enabled: false` suppresses the slide number while keeping the footer line. A semantic `DeckSpec` with no `meta.chrome` compiles to page numbers (title and closing skipped), the `meta.date` footer and, when the deck has sections, the tracker; the raw path stays opt-in. `left_text` always renders on a single line: its box starts at the template's date (`dt`) placeholder and spans the footer (`ftr`) placeholder width (stopping before the slide number); text that is too wide shrinks from 10.5pt down to 8pt. A line that still does not fit gives up fields by priority before anything is cut: `chrome.project_code` first, then `chrome.footer_date` (never the confidentiality marking, the client name or `footer.left_text`), for every slide that shares that footer slot, so the content slides read alike while a section divider with a narrower slot decides only for itself. Only a line with nothing left to drop is ellipsized (`…`). Each case is reported as a review finding, [`CHROME_TRUNCATED`](FIT_FINDINGS.md#chrome_truncated), at `/chrome` (`/footer/left_text` for a legacy-only footer) with the dropped fields and the characters that fit. Content-bearing raw `blank-canvas` slides use `headline`; semantic `DeckSpec` supports flat `slides[]` or chaptered `structure`, plus `meta.required_layouts` for planned canonical-layout coverage. `chrome.tracker: true` sets the current section name above each content slide's title (9pt accent1 caps, +8% letter-spacing, 6pt above the title), from `section_title` or, on a flat deck, the preceding section slide; title, section, closing and agenda slides and slides with an `eyebrow` carry none. A slide's `section_title` is the section name `chrome.section_crumb` appends to its footer; the engine sets it when expanding `structure.sections` and `semantic compile` writes it onto the flat slides it emits, so do not hand-author it. On a flat deck without `section_title`, `chrome.section_crumb` uses the same running section as `chrome.tracker` — the title of the preceding section slide — so both read the same section; title, section, closing and agenda slides keep the deck-wide footer line. See [SEMANTIC_COMPILER.md](SEMANTIC_COMPILER.md) and `get_input_schema` for the complete contracts.

## Validating before generating

- CLI: `json2pptx validate <input.json>` — same validator the engine runs. It also dry-renders every chart and diagram: one that cannot render (an unknown type such as `stacked-bar` for `stacked_bar`, data the renderer rejects) is reported as `diagram_render_failed` at the chart's path with the renderer's suggestion, and the deck is invalid — no flag needed.
- CLI: `json2pptx validate <input.json> --fit-report` — adds the layout-fit diagnostics (text overflow, density, contrast, chart label fit).
- CLI: `json2pptx validate <input.json> --format json` — one JSON shape whether the deck passes or not: `{"valid": bool, …, "findings": {"ok": bool, "summary": "…", "findings": [ … ]}}`. A refused deck, a file that is not JSON (`INVALID_JSON`, with line and column) and a missing file (`FILE_NOT_FOUND`) answer `{"valid": false, "findings": {…}}` on stdout, so `findings.findings` is always the list.
- MCP: `validate_input` — wraps both; with `fit_report: false` it still refuses an unrenderable chart or diagram.

`json2pptx generate` exits non-zero and writes no deck when a chart or diagram fails to render, at every `--strict-fit` level and with `--partial`: a slide carrying a "Data unavailable" placeholder is never a result.

Errors carry structured `code` fields catalogued in `docs/FIT_FINDINGS.md` (with severity and recommended action). The validator accepts both canonical and alias enum values for backward compatibility; the schema publishes only the canonical names.
